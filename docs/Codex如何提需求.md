# Codex 如何提需求

## 推荐沟通方式

不要一上来要求“直接写代码”。先让 Codex 固化事实源：

```text
我要做一个真实功能：<功能名称>。
请先走 OpenSpec，不要直接写代码。
先输出需求理解、功能范围、非范围、表结构影响、API、权限、任务拆分和需要我确认的问题。
待确认问题必须带建议方案、推荐原因、影响范围、可选方案和默认处理。
```

## 命令优先

小白不要手动创建 OpenSpec 目录，优先用统一入口：

```bash
bash scripts/ai-dev.sh init
bash scripts/ai-dev.sh feature <change-id>
```

已有 change 需要重生成骨架时才使用：

```bash
bash scripts/ai-dev.sh feature <change-id> --force
```

`init` 会用编号选择访问控制模式，不需要自己输入 `local`、`external`、`none`。

## 后台功能模板

```text
我要做后台功能：<功能名称>。
项目是 <技术栈>。
请先走 OpenSpec，不要直接写代码。
必须检查访问控制/RBAC、表结构、API 契约、前端页面状态和测试计划。
未知字段、状态、权限、响应格式不要猜，列为待确认问题。
每个待确认问题必须给出建议和好处，方便我选择。
```

## JWT 登录模板

```text
我要做 JWT 登录系统。
请先走 OpenSpec，不要直接写代码。
设计用户表、角色权限、登录 API、刷新/登出策略、Redis 黑名单、JWT claim、安全风险和测试计划。
所有待确认项先列出来，并给出建议方案、推荐原因、影响范围、可选方案和默认处理，确认后再实现。
```

## CRUD 功能模板

```text
我要做 <对象名称> 管理。
请先走 OpenSpec，不要直接写代码。
先确认字段、状态、唯一约束、删除方式、访问控制模式、权限点、列表筛选、分页、排序、表结构、API 和前端页面。
待确认项必须带建议方案、推荐原因和影响范围。
```

## 确认后进入实现

```text
我确认这个 OpenSpec。
请按 tasks.md 最小可验证切片实现，改完跑测试。
实现后准备 deepv4 二审输入，不要自动改业务规则。
```

## 不建议的说法

```text
帮我随便做个登录。
```

问题：会导致 AI 猜用户表、密码规则、token 规则、权限、错误码和响应格式。

```text
直接生成所有代码。
```

问题：没有 OpenSpec，后续无法判断代码是否正确。
