# AI 全栈控制系统使用手册

## 这是什么

AI 全栈控制系统是一套复制到业务项目根目录使用的工程约束和协作流程。

它不是业务框架，也不是运行时服务。它的作用是把 AI 开发拆成可确认、可审查、可验证的步骤：

```text
需求事实源 -> 架构设计 -> 数据库/API/任务拆分 -> Codex 实现 -> 测试 -> deepv4 二审 -> Codex 总审
```

## 角色分工

| 角色 | 负责什么 | 不负责什么 |
|------|----------|------------|
| Codex | 需求澄清、系统架构、表设计、任务拆分、代码实现、测试、最终审查 | 不在规则不清时猜业务 |
| OpenSpec | 记录已确认需求、设计、任务、规格 | 不替代用户确认 |
| deepv4 | 对 diff、测试结果、风险点做二审 | 不直接改代码，不决定业务规则 |
| scripts | 安装、检查、测试、日志摘要 | 不保证业务正确性 |

## 标准开发流程

### 1. 先写事实源

新需求不要直接改代码。先创建：

```text
openspec/changes/<change-id>/proposal.md
openspec/changes/<change-id>/design.md
openspec/changes/<change-id>/tasks.md
openspec/changes/<change-id>/specs/<capability>/spec.md
```

可以从模板复制：

```text
templates/openspec-change/
```

### 2. Codex 做架构和拆分

让 Codex 读取 `AGENTS.md`、`CONTEXT.md` 和对应 OpenSpec change，然后产出：

- 需求理解
- 功能范围
- 表结构影响
- API 影响
- 前后端任务拆分
- 测试计划
- 风险和待确认问题

### 3. Codex 实现代码

你确认 OpenSpec 后，Codex 再按任务最小切片实现。

实现时必须遵守：

- 不猜字段、状态、权限、API。
- 涉及数据库先读数据库工程师 `agents/agent-dba.md`。
- 涉及接口先读 API 契约工程师 `agents/agent-api.md`。
- 改完必须验证或说明无法验证原因。

### 4. 执行测试

统一测试入口：

```bash
bash scripts/run-tests.sh
```

测试命令来自：

```text
.ai-control/project.env
.agent/project.env
PROJECT_TEST_COMMAND='...'
```

### 5. deepv4 二审

如启用 deepv4：

```bash
bash scripts/prepare-deepv4-review.sh
bash scripts/run-deepv4-review.sh
```

deepv4 只看审查输入，不直接修改代码。

### 6. Codex 最终审查

Codex 最终检查：

- 是否符合 OpenSpec。
- 是否有未确认字段、状态、权限、API。
- 是否有 SQL 风险。
- 是否有事务问题。
- 是否有前后端契约不一致。
- 是否有测试缺口。

## 常用命令

```bash
bash scripts/ai-dev.sh init
bash scripts/ai-dev.sh feature login-jwt
bash scripts/ai-dev.sh feature login-jwt --force
bash scripts/ai-dev.sh ready login-jwt
bash scripts/ai-dev.sh test
bash scripts/ai-dev.sh review
bash scripts/ai-dev.sh next
bash scripts/setup-control-system.sh
bash scripts/bootstrap-new-project.sh --project-dir /path/to/project --profile auto
bash scripts/detect-project-profile.sh --write
bash scripts/check-project-ready.sh
bash scripts/agent-check.sh
bash scripts/route-check.sh
bash scripts/docs-link-check.sh
bash scripts/openspec-check.sh openspec/changes/<change-id>
bash scripts/openspec-conflict-check.sh
bash scripts/run-tests.sh
```

小白优先使用 `scripts/ai-dev.sh`。底层脚本用于高级用户排查、CI 或自动化集成。

### OpenSpec CLI 说明

本系统不强依赖 npm 安装的官方 OpenSpec CLI。只使用 `scripts/ai-dev.sh` 时，脚本会直接维护本地 `openspec/` 目录。

需要官方 `openspec` 命令或 slash command 时，再安装：

```bash
npm install -g @fission-ai/openspec@latest
```

新项目如果要用官方 CLI，可以先运行 `openspec init`，再接入本控制系统。已经接入控制系统后，不建议盲目再次运行 `openspec init`，避免覆盖或改写 `openspec/`、`AGENTS.md` 等文件。

### ai-dev.sh 行为说明

- `init` 会让用户用编号选择访问控制模式：本服务 RBAC、外部权限系统、不适用或待确认。
- `init` 会询问是否启用 deepv4；选择启用后输入 `DEEPV4_BASE_URL`、`DEEPV4_API_KEY`、`DEEPV4_MODEL`，脚本会生成 `.agent/deepv4.env`。
- `init` 不带 `--force` 时不会覆盖已有 `openspec/project.md`、`CONTEXT.md`，也不会静默修改已有 `.ai-control/project.env`。
- `init --force` 才会重写项目卡片、上下文、访问控制模式和已有 deepv4 配置。
- `feature <change-id>` 默认保留已有 OpenSpec 文件。
- `feature <change-id> --force` 才会重生成该 change 的 OpenSpec 骨架。
- `next` 按最近修改时间判断当前最可能继续处理的 change。

### project.md 和 CONTEXT.md 分工

- `openspec/project.md` 记录项目定位、技术栈、用户角色、API 规则、访问控制模式和治理规则。
- `CONTEXT.md` 只记录领域术语、状态候选、业务规则待确认项和不能猜测的内容。
- 如果两者冲突，以 `openspec/project.md` 和具体 OpenSpec change 中已确认内容为准。

## 使用原则

- 不确定的业务规则必须先问用户。
- 数据库、API、权限、状态流转必须进入 OpenSpec。
- deepv4 只做二审，不替代 Codex 和用户确认。
- 代码实现必须可测试、可审查、可回滚。
