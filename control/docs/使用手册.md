## 这是什么

一套工程约束和协作流程，把 AI 开发拆成可确认、可审查、可验证的步骤：

```text
你说需求 → AI 影响探测判级 → 你确认（规格 + 验收用例）→ AI 实现
→ 测试自动回填用例状态 → 发布门禁 + 独立二审 → 交付
```

它不是业务框架，不是运行时服务。核心思想：**AI 的自由度和改动的风险成反比**——改文案随便干，动数据库层层确认。

## 你的职责只有两个确认点

| 确认点 | 你确认什么 | 不确认会怎样 |
|---|---|---|
| **OpenSpec change 确认** | 需求理解对不对、验收用例覆盖够不够、判级（lite/完整）合不合理 | AI 禁止写代码 |
| **数据库变更确认包** | 表结构 DDL、回滚 SQL、联动改动 | AI 禁止执行任何 SQL |

其余所有检查（用例回填、SQL 安全、change 合规、影响范围冲突）都是脚本自动拦截，不需要你操心。

## 三种使用方式

### 方式一：AI 应用里说人话（推荐日常使用）

在 Claude Code / Codex / Kimi Code / Cursor / WorkBuddy 里，直接用自然语言：

| 你说 | AI 做 |
|---|---|
| "加个 XX 功能" / "帮我做 XX" | 影响探测 → 判级 → 建骨架 → 给你确认单（标注级别+理由） |
| "改个文案" / "调下样式" | 通常判 lite，30 秒确认单 |
| "测一下" / "验证一下" | 跑测试 + 汇报用例回填结果 |
| "能上线吗" / "发布" | 发布门禁 + 独立二审 + 汇报残余风险 |
| "表要加个字段" | 切数据库工程师，先出表结构设计审查 |

AI 判级必须给理由（基于它探测到的影响文件/表/接口），判错了你一句话纠正即可（"不对，要动表" → 自动升级）。万一 AI 没按流程走，说一句**"按控制系统流程来"**即可拽回。

### 方式二：终端 `./ai` 命令

```bash
./ai new login-jwt          # 建完整变更骨架
./ai new fix-typo --lite    # 小需求快速通道
./ai check login-jwt        # 校验是否可请求确认
./ai test login-jwt         # 跑测试 + 自动回填用例状态
./ai ship login-jwt         # 发布门禁 + 独立二审
./ai sync                   # 改规则后重新生成工具适配文件
./ai doctor                 # 环境体检
./ai install-cli            # 装全局 ai 命令到 ~/.local/bin，免 ./ 前缀
```

### 方式三：底层脚本（CI / 自动化 / 排查用）

见[命令参考](#命令参考)。日常不需要。

## 日常开发：小需求（lite）

适用条件（同时满足）：不碰数据库表/SQL；不碰 API 契约；不碰权限/租户/支付/状态流转；改动范围可明确列出。

```bash
./ai new fix-button-text --lite
```

生成 3 个文件：

```text
openspec/changes/fix-button-text/
├── proposal.md      # 头部标注"变更级别: lite"；需求说明 + 影响范围
├── tasks.md         # 两条任务：实现、验证
└── test-cases.md    # 验收用例（lite 也必须有，哪怕一条手动用例）
```

流程：AI 补全内容 → 你看 30 秒确认 → AI 实现 → `./ai test` → `./ai ship`。

**防滥用门禁**：lite 的影响范围里一旦声明了数据库表或 API（非 none），`impact-check` 直接失败并要求升级完整流程。实现中途发现要碰库，AI 必须停下来告诉你升级。

## 日常开发：标准需求（完整流程）

```bash
./ai new order-export
```

生成五件套，各文件的作用和"你需要看什么"：

| 文件 | 是什么 | 你重点看 |
|---|---|---|
| `proposal.md` | 需求提案 + 影响范围（文件/表/API/页面/agent） | 需求理解对不对、影响范围全不全 |
| `design.md` | 设计说明（跨模块/DB/接口兼容时才有实质内容） | 方案取舍是否认可 |
| `tasks.md` | 任务清单（带验收标准） | 扫一眼即可 |
| `test-cases.md` | **验收测试用例**（用例表 + 覆盖要求） | **重点看**：正常流/异常流/权限/边界覆盖够不够 |
| `specs/<能力>/spec.md` | 能力规格（场景化描述，归档后成为长期事实源） | 状态流转、权限规则是否符合业务 |

流程节点：

```text
./ai new → AI 补全五件套（涉及接口先过 API 契约，涉及页面先过 UI 设计）
→ ./ai check（脚本校验：影响范围齐全、声明与任务闭环、用例覆盖、语言规范）
→ 你确认 → AI 按 tasks.md 最小切片实现
→ ./ai test → ./ai ship
```

## 数据库变更专属流程

只要涉及建表、改字段、加索引、迁移数据，强制两阶段：

**阶段一：表结构设计审查**（AI 输出，等你确认）
查询场景、写入场景、数据量级、逐字段必要性分析、索引建议、冗余字段建议、待确认项。此阶段禁止输出可执行 DDL。

**阶段二：数据库变更确认包**（你确认阶段一后 AI 才输出）
目标结构 DDL、本地手动执行 DDL、rollback SQL、Laravel/Hyperf migration 预览（如适用）、Entity/Mapper/XML/DTO/VO/API 联动清单、风险说明。

**你确认阶段二后，AI 才能执行 SQL 或写 migration 文件。** 硬规则：DROP/TRUNCATE 默认先备份（`原表名_copy_yyyyMMdd`）；禁止全表 UPDATE/DELETE；禁止无 ON 条件 JOIN。完整规则见 `.ai-control/control/rules/10-db-schema.md`。

## 测试用例机制详解

这是本系统区别于"AI 自己测自己"的核心机制：

```text
设计期   测试工程师产出 test-cases.md，随 change 一起经你确认 —— 用例是验收契约
实现期   自动化测试的方法名必须带用例 ID：test_TC01_分页查询（TC01/TC-01/TC_01 均可）
验证期   ./ai test <change-id> → 跑测试 → 解析 JUnit 报告 → 按 ID 自动回填状态为 通过/失败
发布期   ./ai ship → 门禁检查：状态残留"已设计"直接拦截
```

要点：

- **自动回填只认测试报告**——AI 无法"没跑就填通过"；测试失败时也会回填（trap 保证），失败必须修复或明确记录残余风险。
- **"手动"用例永不自动回填**：UI 观感这类自动化不了的，AI/你执行手动步骤后人工回填；门禁保证它不会被遗忘。
- **执行阶段禁止为迁就实现修改已确认用例**；确需修改必须重新经你确认。
- 覆盖硬要求：涉及 API 必须有异常流用例；涉及页面必须有权限态和空态/错误态用例；涉及写操作必须有重复提交/并发用例。

支持 JUnit XML 的框架都能自动回填：Maven Surefire、Jest（jest-junit）、Pytest（--junitxml）、Go（gotestsum）等。报告目录自动搜索 `target/surefire-reports`、`build/test-results`、`test-results` 等常见位置，也可显式指定：

```bash
bash .ai-control/control/scripts/test-cases-sync.sh openspec/changes/<id> path/to/junit-reports
```

## 多工具接入说明

一份源（AGENTS.md + agent 手册），自动生成各工具适配物：

| 工具 | 机制 | 生效方式 |
|---|---|---|
| AI 助手 | 自动发现项目根 AGENTS.md | 装完即生效 |
| Kimi Code | 原生支持 AGENTS.md（项目根/全局/子目录） | 装完即生效 |
| Cursor | 原生支持 AGENTS.md | 装完即生效 |
| Claude Code | `CLAUDE.md`（import AGENTS.md）+ `.claude/agents/` 6 个自动委派 subagent + `.claude/skills/` 3 个技能 | 安装时自动生成 |
| WorkBuddy | `workbuddy-skills/` 7 个 SKILL.md（1 总契约 + 6 角色） | `cp -r workbuddy-skills/* ~/.workbuddy/skills/` 后重启 |

三层加载机制（以 Claude Code 为例）：契约每次对话 100% 加载；6 个角色全部注册、按 description 自动委派、命中时才载入全文；docs 规则由角色手册"必须读取"指路、AI 按需读取——这样约束全生效且不撑爆上下文。

改了 `.ai-control/` 里的规则后运行 `./ai sync` 重新生成；已被你手改的生成物默认跳过不覆盖。

**WorkBuddy 技能是自包含的**：导出时会把各角色引用的规则全文内嵌为附录快照，脱离项目的空工作区也能拿到完整约束（Claude/Codex 等在项目内运行的工具保持引用式，不受影响）。因此规则更新后，除了 `./ai sync`，还需把 `workbuddy-skills/` 重新复制到 `~/.workbuddy/skills/` 并重启 WorkBuddy。

## 独立二审配置与使用

独立二审由另一个 LLM 完成：只看 diff 和测试摘要输出审查意见，不改代码，不替代你的确认。核心原则是**独立**——二审员不能是写代码的那个会话。

四种接法，配置在 `.agent/review.env`（`init` 时可交互配置，权限自动 600）：

| REVIEW_PROVIDER | 说明 | 需要什么 |
|---|---|---|
| `openai-compatible`（默认） | DeepSeek、Kimi、通义、GLM、GPT、Ollama 等任何 OpenAI 兼容端点 | BASE_URL + API_KEY + MODEL |
| `anthropic` | Claude 官方 Messages API | API_KEY + MODEL |
| `claude-cli` | 本机 Claude Code 无头模式，**复用订阅免 API key**，每次全新会话 | 已安装 `claude` 命令 |
| `codex-cli` | 本机 Codex 非交互模式，同上 | 已安装 `codex` 命令 |

API 模式示例：

```bash
REVIEW_PROVIDER='openai-compatible'
REVIEW_BASE_URL='https://your-endpoint/v1'
REVIEW_API_KEY='...'
REVIEW_MODEL='...'
```

CLI 模式只需一行：

```bash
REVIEW_PROVIDER='claude-cli'    # 或 codex-cli
```

WorkBuddy 等无 CLI 的工具走手动：`prepare-review.sh` 生成 `.agent/reviews/review-input.md`，整份粘贴给任意 AI 应用，回复存为 `review-output.md`。

运行：`./ai ship <change-id>`（内含）或单独 `bash .ai-control/control/scripts/run-review.sh`。二审输出末尾带机读结论 `VERDICT: PASS | PASS_WITH_RISKS | BLOCK`，BLOCK 会拦下 ship；确要跳过用 `./ai ship <id> --skip-review "原因"`（留痕）。

**外发安全**（自动生效）：`.env`、密钥文件、生产配置被排除；拼装内容做密钥模式扫描，命中即中止（`REVIEW_ALLOW_SECRETS=1` 显式放行）；diff 超 512KB 截断（`REVIEW_DIFF_MAX_BYTES` 可调）；API key 不落命令行。

## 目录结构说明

```text
项目根/
├── AGENTS.md            总契约（Codex/Kimi/Cursor 自动读）
├── CLAUDE.md            Claude Code 入口（自动生成）
├── CONTEXT.md           领域术语、业务规则待确认项
├── ai                   统一命令入口
├── openspec/            事实源：project.md + changes/ + specs/
│   └── changes/<id>/    变更五件套（lite 为三件）
├── .claude/             Claude 适配（自动生成）
├── workbuddy-skills/    WorkBuddy 技能包（自动生成）
├── .agent/              本地运行数据：review.env、日志、审查输出（已 gitignore）
└── .ai-control/         控制系统本体
    ├── project.env      项目画像（技术栈、测试命令、访问控制模式）
    └── control/         agents/ docs/ scripts/ templates/ tests/ tools/
```

`openspec/project.md` 记录项目定位和治理规则；`CONTEXT.md` 只记领域术语和待确认项；冲突时以 project.md 和已确认 change 为准。

## 常见问题

**Q：AI 没按流程走，直接开始写代码了？**
说"按控制系统流程来"。它会回到意图路由表。

**Q：lite 变更被 impact-check 拦了？**
说明这个"小需求"实际碰了数据库或接口。不带 `--lite` 重新生成完整骨架（`./ai new <id> --force`），走对应确认流程。这是设计行为，不是 bug。

**Q：`./ai ship` 报"仍有用例状态为已设计"？**
两种可能：自动化测试没按约定在方法名里带用例 ID（补上重跑 `./ai test <id>`）；或手动用例还没人工回填（执行手动步骤后把状态改为通过/失败）。

**Q：我手改了 CLAUDE.md / 适配文件，会被 sync 覆盖吗？**
不会。`./ai sync` 内部用 `--force` 重新生成的是它管理的文件；如果你想保留手改，把内容加到源头（AGENTS.md / agent 手册）再 sync 才是正路——生成物不该手改。

**Q：需要装官方 OpenSpec CLI 吗？**
不需要。`ai-dev.sh` 直接维护本地 `openspec/` 目录。需要官方 slash command 时再 `npm install -g @fission-ai/openspec@latest`；已接入后不要盲目运行 `openspec init`，避免覆盖 `openspec/` 和 `AGENTS.md`。

**Q：测试框架不出 JUnit XML 怎么办？**
配置对应插件（jest-junit、pytest --junitxml、gotestsum）；实在没有就把用例验证方式标为"手动"，人工回填。

**Q：怎么升级控制系统？**
当前版本暂无 upgrade 命令（在路线图上）。临时做法：重新运行 install-to-project.sh --backup，冲突文件会先备份。

## 使用原则

- 不确定的业务规则必须先问用户，禁止猜测。
- 数据库、API、权限、状态流转必须进入完整 OpenSpec 流程。
- 测试用例是验收契约：先确认、后实现、报告回填、门禁兜底。
- 独立二审只做二审，不替代用户确认。
- 生成物不手改，改源头后 `./ai sync`。
