# 审查报告：供应商入驻

## 阻塞问题
- 供应商资料字段未确认，不能创建真实表结构。
- 审核状态和状态流转未确认，不能实现状态机。
- API 响应包装、错误码、分页格式和鉴权方式未确认。
- 访问控制模式、责任系统、权限点、菜单权限、按钮权限和越权处理未确认。

## 重要问题
- 审核通过时是否同时创建供应商档案，需要确认事务边界。
- 供应商是否允许重复提交、撤回或重新提交，需要确认业务规则。
- 敏感资料的可见范围、脱敏规则和审计日志需要确认。
- 平台管理是否存在租户、组织或数据范围隔离，需要确认。

## 次要建议
- 可把专家入驻作为独立 change 处理，避免和供应商入驻耦合。
- 可在实现后补充资料变更记录，但需要单独确认审计和可见范围。

## 表结构/字段变化审查
- 示例中的 `supplier_onboarding_application` 和 `supplier_profile` 只是候选表。
- 实现前必须输出 migration SQL、rollback SQL、索引和历史数据兼容策略。
- 审核写操作如果同时更新申请和供应商档案，必须使用事务。

## API/前端契约审查
- `api-contracts/supplier-onboarding.md` 是 OpenSpec 的接口契约展开，不是第二套事实源。
- 供应商端和平台管理端必须分别覆盖加载态、空态、错误态、权限态和重复提交防护。
- 后端必须校验供应商只能访问自己的申请，不能只依赖前端隐藏入口。

## SQL 性能风险审查
- 平台审核列表必须分页，并确认状态、提交时间、租户或组织字段的索引。
- 禁止 `SELECT *`，敏感资料字段必须显式控制返回范围。

## 安全和权限审查
- 供应商只能提交和查看自己的入驻申请。
- 平台管理审核接口必须校验审核权限和按钮权限。
- 敏感资料不得返回给未授权角色，日志不得输出完整证件或附件敏感信息。

## 验证步骤
- 审查 OpenSpec change。
- 审查 API contract。
- 确认字段、状态、权限和响应格式后再实现。
- 实现后运行测试、SQL 安全检查、访问控制检查和 deepv4 二审。

## 风险总结
- 本示例保留多个待确认项，真实项目必须先补齐业务字段、权限、状态、响应格式和数据库设计，再进入代码实现。
